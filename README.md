# Проверка регрессии качества AI-приложения

Это самостоятельный пример XNova для сравнения двух версий приложения по одним и тем же шести сценариям. **Все ответы и записи `executed_tools` синтетические**: проект не вызывает LLM, не измеряет реальные модели, не требует API-ключей или платных сервисов.

`baseline` обозначает исходную версию, `candidate` — версию перед выпуском. В `examples/golden.json` записаны вопросы, правила оценки и критичность каждого case ID. `examples/baseline.json` и `examples/candidate.json` содержат заранее подготовленные наблюдения с одинаковыми версиями набора, evaluator, промпта, инструментов и документов. Отличается только метка модели.

## Запуск

Установите Python 3.12 или новее. Основной пример использует стандартную библиотеку; для контрольных тестов нужен `pytest==9.1.1`. После клонирования выполните:

```bash
git clone https://github.com/xnova-tech/llm-regression-evaluation-example.git
cd llm-regression-evaluation-example
python -m pip install -r requirements-dev.txt
python examples/compare.py
python -m pytest -q examples/test_compare.py
python examples/compare.py --ci
```

На Windows вместо `python` при необходимости используйте `py -3.12`. Первая команда печатает покейсовый отчёт и завершается кодом `0` даже при `BLOCK`: это режим просмотра. Тесты проверяют основной результат, отрицательные случаи и решения gate. Последняя команда возвращает код решения для CI: `0` — `RELEASE`, `1` — `BLOCK`, `2` — `REVIEW`. Для поставляемого candidate ожидается `1`.

Обе версии имеют `5/6 PASS`. При этом `cross_tenant_access` меняется с `PASS` на `FAIL`, а `renewal_ambiguity` — с `FAIL` на `PASS`. Критическая регрессия доступа даёт `BLOCK`; улучшение другого ответа её не компенсирует. Отчёт также показывает число `UNDETERMINED` и классификацию каждого перехода.

Для проверки кодов завершения и текста отчёта одной командой запустите `python check_cli.py`. Именно эту проверку и unit-тесты запускает GitHub Actions на Linux, macOS и Windows с Python 3.12. Намеренный `BLOCK` считается успешно проверенным, когда процесс возвращает `1`.

## Свои данные

Сохраните копии трёх JSON-файлов и замените в них сценарии и наблюдения, сохранив структуру полей. Каждый `id` в `golden.json` должен быть уникальным; ответы сопоставляются с ними по ID. Обновите `dataset_version` и `evaluator_version` одновременно в наборе и обоих файлах наблюдений. Остальные версии конфигурации и параметры генерации должны совпадать между baseline и candidate для сопоставимого сравнения. Затем запустите те же команды из каталога проекта.

Проверка `terms` ищет фрагменты строки и не доказывает истинность произвольного ответа. `executed_tools` в этих JSON заполнен вручную и не подтверждает исполнение серверного инструмента. В рабочем приложении его нужно брать из доверенного серверного trace и, где применимо, сверять с изменением состояния. Один синтетический прогон не показывает вариативность живой модели, не измеряет качество на пользовательском трафике и не заменяет независимую проверку безопасности.
